# ADR 0003 — Authentication

- Status: superseded for identity by [ADR 0007](0007-supabase-environments.md) (Supabase Auth). Membership, roles, and org resolution in this ADR still apply.
- Date: 2026-08-26
- Week: 1

## Context

Buyers must self-host without a Clerk/Auth0 bill. We need credentials, magic-link (SMTP), and optional OAuth. Sessions must carry enough to resolve membership and the active organization.

## Decision

**Identity** is Supabase Auth (ADR 0007): email + password, magic link, optional OAuth flags on the project.

**Authorization** is unchanged: roles live on `membership` (`owner`, `admin`, `template_manager`, `inspector`, `reviewer`, `client_viewer`). Route handlers and repositories check role + org.

Session cookies come from `@supabase/ssr` (httpOnly). Service role never ships to the client.

Invitations: tokenized email, membership row `invited` → `active`. Super-admin is a platform flag off the tenant membership table.

## Consequences

- Auth.js is not installed in Week 2. Revisit only if we add a non-Supabase identity adapter later.
- Magic links depend on the linked project’s email settings, not Mailpit.
- Client viewer can exist as a Supabase user with `client_viewer` membership and magic-link-only access.

## Alternatives rejected

- Auth.js v5 as the identity layer on top of Supabase Postgres: duplicate session stacks (see ADR 0007).
- Pure JWT in localStorage: harder revocation, XSS-shaped sessions.
- RLS as the only authorization: never-cut tenant isolation still lives in repositories.
